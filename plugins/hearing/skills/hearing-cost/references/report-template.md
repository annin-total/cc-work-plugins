# 調書テンプレート（大まかな型。厳格にしない）

統一感を持たせるための型であり、書き方の基準でもある。
結論を先頭に置き、冗長に書かない。見出しは足し引きしてよい。1〜2 ページに収まる量を目安にする。

## 書くこと
- 重そうな要因と、その確度（観測／推定／利用者談）。機械の集計（観測）と利用者談は区別して書く
- 要因ごとに「業務上必要そう／避けられそう／判断できない」の 1 語（任意。決めつけない）
- 利用の全体像（モデルのファミリー比、effort の分布、トークン量は種別ごと、セッションの長さと頻度、区切り操作 clear・compact の回数をセッション数や長さに照らして、起動のしかたの内訳）
- 履歴に残る項目は 3 値で:「観測（N 件）」「記録なし（版が古い等）」「0 件（記録あり）」。「記録なし」を「低い」「0%」と書かない
- スキル・MCP の使われ方。名前を出してよい（冗長なワークフローや無関係な発火の指摘に役立つ）。重要でないものは件数や分類にまとめる。分からなければ「不明」でよい
- 利用者から聞いた背景（要点を一般用語で）
- 改善の候補（控えめに。断定しない）
- 制約（欠損、読めなかったもの、除外したもの、検証で残った注意）と来歴

## 書き方の指針
- 大まかな概要に抽象化し、重要でない情報は捨てる。基本は固有名詞を書かず、本質的な内容を「具体的かつ一般用語だけ」で書く。
  例:「LP のデザインガイドライン作成」「ツール管理台帳の Excel データの集計と検知」
- 必要なら固有名詞を最小限書いてよい。
- 抽象化しすぎない。「開発」「文書作成」のような、一般に自明なことしか分からない書き方にしない（先回りして伏せない）。

## 避けること（禁止ではない）
- 本文の長い逐語引用、重要でない固有名詞・パス・コマンド
- 全件の一覧、検証や分析の過程
- 利用者を責める表現、断定

## 書かないこと
- 認証情報・秘密の値（鍵・トークン・パスワード等）
- 金額、単価、トークン種別の合算値

珍しい拡張子は「その他」にまとめる。順位は概算で、内部の重みは持たない（確度は「推定」）。時間帯・曜日・日別の分布は要因の説明に役立つときだけ書く（任意）。
配置前に未記入の `＜＞` を残さない。履歴が少ない（セッションが数件など）ときは、そのまま書き、「データが少ないため参考程度」と制約欄に一言添える。

# Claude Code 利用ヒアリング調書

対象者: ＜氏名（ファイル名と同じ値）＞　／　作成日: ＜YYYY-MM-DD＞　／　期間: ＜開始日〜終了日＞（この端末の履歴のみ）
位置づけ: 履歴からの概算・推測。参考資料であり、数値は「だいたい」。

## 1. 結論
＜カバー率が水準未満なら先頭に「部分的な集計」と書く＞
＜重そうな要因を大きい順に 2〜4 行。それぞれに確度と 1 語を添える。例:「長いセッションの継続が主因と推定（観測／業務上必要そう）」＞

## 2. 利用の全体像
- 期間・セッション数・稼働日数: ＜＞
- 主な用途: ＜具体的な作業内容を一般用語で＞
- セッションの長さ: ＜＞（定義: 行の間隔が 30 分を超えたら分割し、稼働時間を足したもの）
- モデルのファミリー比: ＜各ファミリー／その他 Claude／非 Claude／不明。件数併記＞
- effort の分布: ＜観測（N 件）／記録なし／0 件（記録あり）＞
- トークン量（種別ごと。合算しない）: 新規入力 ＜＞／出力 ＜＞／キャッシュ書き込み ＜＞／キャッシュ読み込み ＜＞
- transcript 外・過小分: ＜補助モデルの消費や、サブエージェントの出力トークンが transcript 上は過小な分があれば、cost-state との差を注記（推定）＞
- スキル・拡張の使われ方: ＜目立つものは名前と頻度。分からなければ「不明」＞
- 区切り操作: ＜clear／手動 compact／自動 compact の回数と発生セッション数。記録なしの版は明記＞
- 起動のしかた: ＜対話（cli）／`claude -p`・SDK など自動実行のセッション数と API 呼び出し数。記録なしは明記＞

＜用語説明（必要なら数行）: キャッシュ読み込み・書き込み、サブエージェントなど＞

## 3. 重さの要因
＜要因ごとに「観測 → 解釈（その作業で何をしていたか）→ 確度 → 1 語」を 2〜3 行。種別ごと（出力・キャッシュ書き込み・新規入力）の上位セッションの寄与が全体の約 1 割以上のものは構造や用途まで掘る＞

## 4. 利用者からの補足
＜聞いた業務背景・使い方の要点を数行（利用者談）＞

## 5. 改善の余地（候補）
＜観測に対応づけて数件。「〜かもしれない」の温度感。業務上必要な使い方ならそれ自体を所見にする＞

## 6. 制約・注意
＜保持期間による欠損の疑い／除外した自セッション／カバー率と読めなかったデータ／組織側の集計との突き合わせはしていない／検証で残った指摘＞
