# 自作の hook・スキルをプラグインにする

利用者の手元で動いている hook・スキルを、マーケットプレイスの 1 プラグインとして取り込み、PR を出すまでを行う。
新しく作る機能ではなく、**既にあるものを移して整える**作業である。元のファイルは変更せず、コピーを調整する。

判断の要点（両 OS 対応・端末固有の値の置き換え・hook の Python の起動・構成）は [references/conventions.md](references/conventions.md) にある。
対象リポジトリに規約文書（ルートの CONVENTIONS.md・CLAUDE.md など）や雛形・検証スクリプトがあれば、**そちらを優先する**。

質問は選択肢と推奨を添えて尋ねる。書き込みの前に、何をどこへ書くかを示して承認を得る。
途中で一覧に無い判断が要るようになったら、自分で決めずに尋ねる。
利用者の git の設定（リモート・追跡先・config）は、道筋に書いた操作のほかは変えない。
一時ファイル（退避・PR 本文など）は対象リポジトリの外の、この作業専用のディレクトリに置き、終わったら消す。

## 道筋

### 1. 対象を決める

- **取り込むもの**: 利用者が指したファイル・ディレクトリ。hook なら、登録している settings の該当エントリも読んで、イベント・matcher・起動方法を把握する。指定が曖昧なら候補を挙げて尋ねる
- **マーケットプレイス**: 指定が無ければ annin-total/cc-work-plugins
- **作業場所**: 今のディレクトリがそのマーケットプレイスの clone（`origin` の URL で判断）ならそこを使う。違えば clone 先を尋ねる。URL で判断できない（ローカルのリポジトリ・社内のホストなど）ときは、ここでよいかを尋ねる
- 作業ツリーに未コミットの変更があれば、触らずに止めて扱いを尋ねる

### 2. 規約を読む

対象リポジトリの README・規約文書・雛形・既存プラグインを読み、構成と書き方の流儀をつかむ。既存プラグインは、似た性質のもの（hook を持つもの、スキルだけのもの）を 1 つ見れば足りる。

### 3. 調整の案を出す

元のファイルを読み、次を洗い出して、一覧にして利用者に示す。案に合意を得てから書く。

- **秘密の値**（トークン・Webhook の URL・パスワードなど）: 値はリポジトリに入れない。機能に要るなら各利用者が入れる設定（`userConfig` の `sensitive`）にし、要らないなら機能ごと外す。見つけた場所を伝え、元ファイルの値の扱い（無効化など）は利用者に任せる
- **端末固有の値**（絶対パス・ユーザー名・ホームの場所・社内のホスト名や組織名・特定の Python の場所）: 設定（`userConfig`・環境変数）か自動検出に置き換える。社内の名前は一般的な表現にするか、設定に逃がす
- **片方の OS でしか動かない書き方**: references の具体則に照らして直す
- **取り込み方**: hook は既定で `hooks/hooks.json`。Git Bash の無い Windows でも確実に動かしたい等の理由があれば導入スクリプト方式。どちらにするかと理由
- **配布物の範囲**: 評価用のファイル・開発用のメモなど、配布物に入れないもの（テストへ移す・持ち込まない）
- **プラグイン名・スキル名**: 元の名前から変えるか（接頭辞を外す等）。既存と衝突しないか。呼び出しは `/<plugin>:<skill>` になる

挙動を変える調整（出力の場所が変わる、OS によって機能が欠ける等）は、変えてよいか個別に尋ねる。

### 4. 作業ブランチを切る

既定ブランチは `main` とは限らない。`git symbolic-ref refs/remotes/origin/HEAD`（GitHub なら `gh repo view <owner/repo> --json defaultBranchRef` も）で確かめ、`git fetch` してからその先端から作業ブランチを切る。

### 5. 取り込む

合意した案のとおりに、プラグインのディレクトリへコピーして調整する。あわせて、対象リポジトリの流儀に従って次をそろえる。

- マニフェスト（`version` を含む）・プラグインの README（前提・使い方・費用や送信先・Windows 実機での確認状況）
- マーケットプレイスへの登録、ルート README の一覧
- テスト（調整した箇所が両 OS で通ることを確かめるもの。置き場所は対象の規約に従う）

### 6. 確かめる

対象リポジトリの検証スクリプトがあれば実行し、全部通す。無ければ references の検証手順に従う。
hook は、渡される入力を模した stdin でスクリプトを実際に起動し、終了コードと出力を見る。通知・外部への送信など副作用のある処理は、偽のコマンドやローカルの受け口に差し替えて確かめ、本物の送信先には向けない。

### 7. PR を出す

コミットし、push して、既定ブランチ宛てに PR を作る。PR テンプレートがあればその形式で書く。
チェックリストは、確かめた項目にだけ印を付ける。CI でしか確かめていない OS は、実機で確かめたと書かない。
CI があれば結果を待ち、落ちたら直す。マージはしない。

利用者には、PR の URL と、確かめていないこと（特に Windows 実機での動作）、元ファイルに残っている秘密の値や、プラグインを入れた後に元の hook 登録を外す必要があること（二重に動くため）を伝える。
